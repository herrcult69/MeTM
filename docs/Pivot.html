Trudy pivot options

Should Trudy stay a hand-rolled Java relay, go hybrid with Wireshark, or move to Ettercap/Bettercap? What changes, and what to expect, under each.

Why this came up: eavesdropping and active tampering have different minimum requirements. Passive eavesdropping only needs traffic to physically flow through Trudy's machine (ARP spoof + IP forwarding) — no application-layer relay at all. Active tampering/forging needs something that actually terminates and rewrites the stream, which is where a real tool choice exists.

A. Keep Trudy.java as-is

The custom Java relay, now fixed (closed-socket-after-accept, connect-retry, heartbeat-based fast failure detection). Full control, exactly matched to the app's line protocol.

  • Pros: /toalice / /tobob live, typed-on-the-spot forged injection exactly as already documented. Zero new tools to learn before presenting.
  • Cons: it's still hand-rolled networking code you own if anything else surfaces — and several real bugs already came from exactly that (see footer).

B. Hybrid — Wireshark for eavesdrop, keep the relay for tampering

Recommended

Split the demo into two phases instead of one continuous attack.

Phase 1 — eavesdrop (zero code)

  • arpspoof + net.ipv4.ip_forward=1, but no iptables REDIRECT, no Trudy process at all. Traffic still reaches the real Bob untouched — ARP spoofing just makes it pass through Trudy's NIC first.
  • Open Wireshark on the Kali interface, filter tcp.port==9000, right-click a packet → Follow → TCP Stream. The live conversation scrolls by in plaintext.

Phase 2 — tamper / drop / forge (unchanged)

  • Add the iptables REDIRECT rule, start Trudy.java exactly as already built and fixed. Nothing new here.

What to expect

  • The heartbeat noise (\u0001HB, ~700ms each direction) will show up raw in Wireshark's Follow-Stream view — Wireshark has no app-level knowledge to filter it the way Trudy's own console now does. Either explain it live ("that's our keep-alive ping, ignore it") or add a Wireshark display filter beforehand.
  • You're driving a GUI tool live during the demo instead of a terminal — rehearse it, but there's nothing to debug in it; it's not code you wrote.
  • Net risk: low — this only removes a working piece from one phase; nothing new is built.

C / D. Replace Trudy.java entirely — Ettercap / Bettercap

Higher risk this close to presenting

What changes

  • Trudy.java goes away. Ettercap does the ARP spoofing itself (replacing arpspoof), plus an etterfilter script — a small DSL, compiled with etterfilter script.ecf -o script.ef — that matches and rewrites TCP payloads live:
if (ip.proto == TCP && tcp.dst == 9000) {
    if (search(DATA.data, "love")) {
        replace("love", "hate");
        msg("tampered a line\n");
    }
}
sudo ettercap -T -q -i eth0 -F script.ef -M arp:remote /192.168.0.123// /192.168.0.152//

One tool now replaces arpspoof + iptables REDIRECT + the entire Java relay.

What to expect — the real cost

  • Loses live, typed-on-the-spot forgery. /toalice / /tobob let you type an arbitrary forged line during the demo, reacting to whatever was just said. Ettercap's filters are compiled rules decided in advance — forging becomes "the moment text contains X, inject Y," scripted and rehearsed, not typed live.
  • New unknowns to validate before presenting: etterfilter syntax has real sharp edges — matching the right direction with tcp.src/ tcp.dst, payload offsets, and same-length replacement requirements (a differently-sized replacement string gets fiddly fast). Trading bugs you understand for bugs in a DSL you don't have muscle memory in yet.
  • Bettercap specifically: weaker fit. It's built around HTTP(S) proxying and network recon, not arbitrary custom raw-TCP protocols — supporting this chat app properly would likely mean writing a Go module/plugin, which is more custom code than what exists today, not less. Dropped from serious consideration here.
  • Net risk: medium–high — real payoff (a recognizable industry pentest tool, zero relay code) but real new-unknowns cost, and it changes what the signature "forge a message" demo beat looks and feels like.
Verdict: go with B, the hybrid. It's the only option that reduces risk this close to the deadline — it removes code from the part that's safe to remove (eavesdropping needs no app-layer relay at all) and keeps the part that's already fixed and working (tampering/forging) exactly as it is today. Ettercap is a legitimate, more "textbook pentest tool" demo with another week of rehearsal time, but swapping the forge mechanism and learning a new filter DSL days before presenting tends to eat the time it was supposed to save.
