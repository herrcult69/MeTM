How a man-in-the-middle works

Alice wants to talk to Bob. Trudy lives in the same house, is a hacker and a network expert, and wants to read what they say. This guide walks through the setup, the attack, and the Java simulation that models it. Click the buttons in each section to step through things.

Scope of this lesson. The real attack works at the link layer (ARP spoofing). Our Java simulation does not implement ARP. It assumes the redirect has already happened and models only what Trudy does next: accept Alice's connection, read it, and forward it to Bob over sockets. Sections 3 and 4 show exactly where that line sits.

1. The cast

WhoRoleAddress in our simulation

TrudyAttacker on the same LAN. Sits in the middle and relays everything.Listens on 9000 (where Alice thinks Bob is) and forwards to Bob on 9002

Trudy's goal is to be in the path without either side noticing. She does not need to break any cryptography in the plain setup, because nothing is encrypted. She just has to be in the middle.

2. The house LAN: what it does not protect

Alice, Bob and Trudy share one home network (LAN). Trudy, a network expert, has configured it so that none of the following security properties exist. Each row is a property a network or protocol could have, and whether this house has it.

#Missing propertyWhat it would provideWould it stop Trudy?
1Confidentiality (no encryption)Only the intended receiver can read the bytes. Traffic is plain TCP text.Yes. Trudy can read everything.
2Integrity (no message check)Receiver can detect that a message was changed in transit.Yes, for tampering. Trudy could change messages undetected.
3Endpoint authenticationAlice can verify she is really talking to Bob, and Bob can verify who Alice is.Yes. Bob accepts any connection; Alice accepts any server on port 9000.
4Certificate validation (TLS / PKI)A server proves its identity with a certificate signed by a trusted authority.Yes. There is no certificate for Alice to check.
5ARP authenticationDevices only accept ARP replies they asked for, or that are signed.Yes. ARP replies are accepted without any check. (Out of our simulation.)
6Static ARP entriesAlice and Bob have fixed, hand-set MAC addresses, so their ARP caches cannot be changed.Yes. The cache can be overwritten.
7Dynamic ARP Inspection (switch)The switch checks ARP replies against a trusted IP-to-MAC table and drops forged ones.Yes. Forged replies reach their targets.
8Network segmentation / client isolationDevices cannot see each other's traffic unless the switch sends it to them.Yes. Trudy shares a broadcast domain with Alice and Bob.
9Out-of-band verificationAlice and Bob confirm a fingerprint or code over another channel (phone, in person).Yes. Nothing is compared out of band.
10Replay protectionEach message carries a sequence number or nonce so a replayed copy is rejected.Not used by our simulation, but Trudy could resend captured messages.
Why this list matters. The attack needs only one gap to work. Rows 1 and 3 alone are enough for Trudy to eavesdrop and impersonate. The rest are what a real defense would add in depth.

What Alice and Bob each know

Alice opens a connection and gets replies, so she trusts the replies. But nothing in the exchange proves the other end is Bob. Trudy's relay produces exactly the same bytes that a direct connection would, so the two sides see no difference.

4. What our simulation models (and what it does not)

Stage of the attackIn the real attackIn our Java simulation
Redirect Alice to Trudy ARP spoofing: Trudy answers Alice's "who has Bob's IP?" first, then poisons Bob's cache too. ARP, out of scope Hardcoded. Alice.java line 15 sets port = 9000. Alice is simply told Bob is there.
Trudy receives Alice's messages Frames reach Trudy's MAC address because of the poisoned cache. Trudy's ServerSocket on 9000 accepts Alice's TCP connection. Trudy.java
Trudy reads and forwards Trudy reads the IP packets and re-sends them to Bob. Trudy reads each line with readLine(), logs it, and writes it to Bob's socket. Trudy.java
Bob replies Bob sends his reply to Trudy's MAC (poisoned), and Trudy forwards it to Alice. Bob replies OK, received: ... and Trudy relays it back to Alice. Bob.java
Neither side notices Both think they talk directly. Same. Alice and Bob never receive any notice that Trudy is there.
Honest limitation. The simulation also does not encrypt or check anything, so it proves that Trudy can read traffic in plain text. It does not prove that any particular defense works. Section 6 is a conceptual lab, not a test of the Java code.

7. Code walkthrough

Three files in src/main/java/com/herrcult69/metm/, plus a tiny shared logger (Log.java) that prints timestamps and a tag such as [Trudy].

Alice: where she thinks Bob is

String host = "localhost";
int port = 9000;            // Alice believes Bob is here

Alice reads a line from the keyboard, sends it, and waits for one reply line. She stops when she types EOF END.

Trudy: listen on 9000, then relay

try (ServerSocket server = new ServerSocket(listenPort)) {   // 9000
    ...
    try (Socket fromAlice = server.accept()) {
        relay(session, fromAlice, bobHost, bobPort);            // 9002
    }
}

// inside relay():
while ((message = aliceIn.readLine()) != null) {
    Log.info(TAG, "Alice -> Bob #" + relayed + ... + message);  // Trudy SEES the plaintext
    bobOut.println(message);                                    // forward it
    String reply = bobIn.readLine();                            // wait for Bob
    Log.info(TAG, "Bob -> Alice #" + relayed + ": " + reply);   // Trudy SEES the reply
    aliceOut.println(reply);                                    // pass it back
}

The key line is the Log.info call. Trudy does not need to break anything. The bytes arrive as plain text, so she can read them as they pass.

Bob: reply to every message

while ((message = in.readLine()) != null) {
    if (message.equals("EOF END")) break;
    String reply = "OK, received: " + message;
    out.println(reply);
}

Bob accepts the connection without asking who is on the other end. This is the missing endpoint authentication from row 3 of section 2.

Protocol rules to notice

  • Line-based. readLine() splits on newlines, so a message cannot contain a line break.
  • One reply per message. Alice waits for a reply before she sends the next line, and so does Trudy.
  • End marker. EOF END is forwarded to Bob but gets no reply.
  • One session at a time. Trudy and Bob handle one connection in their loops. A second client waits until the first finishes.

8. Run it yourself

Open three terminals in the repository root. Build first, then start the programs in this order: Bob, then Trudy, then Alice. Build instructions are in README.md.

java -cp target/classes com.herrcult69.metm.Bob
java -cp target/classes com.herrcult69.metm.Trudy
java -cp target/classes com.herrcult69.metm.Alice

What to look for

Type hello in Alice's window. The log lines below show the shape of what you should see. Timestamps and the ephemeral port numbers will differ on your machine.

[Alice] Alice> hello
[Trudy] Alice -> Bob #1 (5 chars): hello  Trudy reads it
[Bob] received #1 (5 chars): hello
[Bob] replied #1: OK, received: hello
[Trudy] Bob -> Alice #1: OK, received: hello  Trudy reads it
[Alice] reply #1: OK, received: hello
Discussion. Alice's log shows a normal-looking reply. Nothing in Alice's output tells her that Trudy is in the middle. That is the lesson: the attack is visible only to Trudy's log.

Exercise: Type something sensitive. Check that Trudy's log contains it in plain text.

9. Quiz

10. Glossary

ARP (Address Resolution Protocol)
Maps an IP address to a MAC address on a LAN. Devices broadcast a question ("who has this IP?") and accept any answer. There is no built-in check.
ARP spoofing / poisoning
Sending forged ARP replies so that a device's cache points an IP address at the attacker's MAC address.
MAC address
The hardware address of a network interface. Used for delivery on the local network.
IP address and port
The network address of a host and the number of the service on it. In our simulation, localhost:9000 is Trudy and localhost:9002 is Bob.
Socket
A program's endpoint for network communication. ServerSocket waits for connections; Socket connects.
Man-in-the-middle (MITM)
An attacker who sits between two parties and can read, change, or block their messages while both believe they are talking directly.
Eavesdropping
Reading traffic that is not meant for you. Prevented by encryption (confidentiality).
Integrity
Detecting whether a message was changed. A MAC or digital signature provides this, but it does not hide the content.
TLS and certificates
Encrypts a connection and lets the client verify the server's identity with a certificate signed by a trusted authority.
Dynamic ARP Inspection (DAI)
A switch feature that drops ARP replies that do not match a trusted IP-to-MAC table.
Broadcast domain
The set of devices that receive each other's broadcast frames. Everyone on the same LAN segment is in it, including Trudy.
Relay (proxy)
A program that receives data on one connection and forwards it on another. Trudy's program is a relay.
